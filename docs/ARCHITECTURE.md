### ერთ სასტუმროზე მიბმული ადგილები (უნდა გადაკეთდეს)

1. **ბაზა:** 15 ცხრილიდან არცერთს არ აქვს `tenant_id`. გასაღებები მოკლეა (ნომერი `'1'`, პარამეტრი `k`), ამიტომ ორ სასტუმროს შორის ერთმანეთს გადაეფარება.
2. **სეზონები კოდშია:** ახალი წელი 25.12–7.01, ზამთარი დეკემბერი–მარტი, ზაფხული ივნისი–აგვისტო. ეს ბაკურიანს მოერგება, ბორჯომს ან ბათუმს არა. სეზონები სასტუმროს პარამეტრი უნდა გახდეს.
3. **სანიმუშო ნომრები და ფასები** (`DEFAULT_TYPES`, `DEFAULT_ROOMS`) და ერთჯერადი მიგრაცია `migrateRooms` ვილა ჯიჯისაა.
4. **საიდუმლოები env-ში:** `ADMIN_PASSWORD`, `META_PAGE_TOKEN` თითო საიტზე ერთია. ბევრ სასტუმროს თითო თავისი სჭირდება.
5. **ტექსტები კოდში:** FAQ `meta.js`-ში („ვილა ჯიჯიში კვება არ არის…“), JSON-LD `index.html`-ში, მფლობელის სახელი „მირზა“ `users.js`-ში, დომენი `_middleware.js`-ში. სულ 230-ზე მეტი ადგილი.
6. **ფოტოები D1-ში BLOB-ად:** ერთ სასტუმროზე ეს მუშაობს, მაგრამ 50 სასტუმრო × 50 ფოტო × ~300 KB უკვე 750 MB-ია.
7. **ბაზის შექმნა პირველ მოთხოვნაზე** (`ensureDb`, `ALTER TABLE … try/catch`): ერთ ბაზაზე ეს მოსახერხებელია, საერთო ბაზაზე კი სახიფათო. საჭიროა ჩვეულებრივი მიგრაციები (`wrangler d1 migrations`).

## 2. მთავარი გადაწყვეტილებები

### 2.1 ერთი Worker, ერთი D1, ყველგან `tenant_id`

- **Pages-ის ნაცვლად Worker სტატიკური ფაილებით (Workers Static Assets).** ამის მიზეზი ისაა, რომ `*.visit2.ge` ქვედომენებზე wildcard მარშრუტი და მომხმარებლების საკუთარი დომენები Worker-ზე მარტივად ეწყობა. კოდი თითქმის იგივე რჩება: `onRequest` ფუნქციები ერთ მარშრუტიზატორში გადავა.
- **ერთი საერთო D1 ბაზა**, ყველა ცხრილში `tenant_id`. D1-ზე „ბაზა თითო სასტუმროზე“ ტექნიკურად შესაძლებელია, მაგრამ მიგრაციებს და კატალოგის ძებნას (ყველა სასტუმროში ერთდროულად) ძალიან ართულებს. 50–500 სასტუმროსთვის ერთი ბაზა საკმარისია.
- **ფოტოები R2-ში** (`tenants/{id}/…`): უფასოდ 10 GB, გადმოწერის საფასურის გარეშე. პირველ ვერსიაში ფოტოები ჯერ D1-შია (როგორც ვილა ჯიჯიზე), რადგან R2-ის ჩართვას ანგარიშზე ბარათი სჭირდება.

### 2.2 Cloudflare Workers Paid, $5 თვეში (გადასაწყვეტია)

ბრიფში წერია „ფასიანი სერვისები არ გამოიყენება“. Visit2-ისთვის კი გეგმა გირჩევ, დაახლოებით 13₾ თვეში:
- უფასო გეგმაზე D1 ბაზის ზღვარი **500 MB-ია**, ფასიანზე **10 GB**;
- უფასო გეგმაზე დღიური ლიმიტის ამოწურვისას ბაზა **ყველა სასტუმროსთვის ერთად** ჩერდება დღის ბოლომდე. ფასიანზე ზედმეტი უბრალოდ ცოტა ძვირდება;
- ერთ მოთხოვნაზე 50-ის ნაცვლად 1000 ქვემოთხოვნა, რაც კატალოგის ძებნას სჭირდება.

ბრიფის 9-ე ნაწილის ~$150 ხარჯში ეს თანხა ისედაც ეტევა (Cloudflare: $0–10).

### 2.3 დომენები

- **ქვედომენი ყველას:** `{slug}.visit2.ge`, მაგალითად `jiji.visit2.ge`. Worker-ის wildcard მარშრუტი `*.visit2.ge/*` და wildcard DNS ჩანაწერი.
- **საკუთარი დომენი** (`villajiji.com`): Cloudflare for SaaS, Custom Hostnames. პირველი **100 დომენი უფასოა**, შემდეგ $0.10 თითოზე თვეში. მფლობელი თავის დომენზე ერთ CNAME ჩანაწერს ამატებს, SSL ავტომატურია. დომენის მთავარ მისამართზე (`villajiji.com` `www`-ის გარეშე) CNAME ყველა რეგისტრატორთან არ მუშაობს; მარტივი გზაა `www.` და მთავარი მისამართიდან `www`-ზე გადამისამართება.
- `visit2.ge` და `www.visit2.ge`: კატალოგი და მფლობელების გვერდი.
- **ადმინი თითო სასტუმროს საკუთარ მისამართზეა:** `{slug}.visit2.ge/admin`, როგორც ვილა ჯიჯიზე. ქუქი ამ მისამართს ეკუთვნის და ხელმოწერილია სასტუმროს id-ით, ამიტომ სხვა სასტუმროზე არ მუშაობს. (თავდაპირველად `app.visit2.ge` ეწერა; პირველ ვერსიაში ეს უფრო მარტივია, ბევრი სასტუმროს მფლობელისთვის საერთო შესვლა შეიძლება მოგვიანებით დაემატოს.)
- **წინასწარი ნახვა** domain-ის გარეშე: `visit2.<ანგარიში>.workers.dev/h/{slug}/`.

### 2.4 როგორ პოულობს მოთხოვნა სასტუმროს

```
მოთხოვნა → Worker
  host = "jiji.visit2.ge" ან "villajiji.com"
  tenant = SELECT … FROM domains WHERE host = ?   (კეში Worker-ის მეხსიერებაში, 60 წამი)
  ვერ მოიძებნა → 404 გვერდი „ეს სასტუმრო ვერ მოიძებნა“
  tenant.status = 'paused' → საიტი „სეზონი იხსნება X-ში“ (ბრიფის მე-2 ნაწილი)
  ყველა შემდეგი ფუნქცია იღებს t = { id, slug, settings … }
```

**ყველაზე დიდი რისკი სხვისი მონაცემების გამოჩენაა.** ერთი დავიწყებული `WHERE tenant_id = ?` და სასტუმრო სხვის ჯავშნებს დაინახავს. ამიტომ:
- SQL იწერება მხოლოდ ერთ ფაილში (`src/db/`), ფუნქციებით, რომლებიც პირველ არგუმენტად `t`-ს იღებენ;
- ტესტი, რომელიც კოდის ყველა SQL-ს ამოწმებს: თუ ცხრილს `tenant_id` აქვს, მოთხოვნაშიც უნდა ეწეროს;
- ტესტი ორი სასტუმროთი: A-ს ადმინი B-ის ჯავშანს ვერ ხედავს, ვერ ცვლის და ვერ შლის.

### 2.5 მონაცემთა მოდელი

ახალი ცხრილები:

```sql
tenants      (id, slug UNIQUE, name, city, status, plan, trial_ends, paused_until, stripe_customer, created)
domains      (host PRIMARY KEY, tenant_id, kind 'sub'|'custom', verified)
users        (id, email UNIQUE, name, salt, hash, ver, created, last_login)   -- ერთი ადამიანი, ერთი შესვლა
memberships  (tenant_id, user_id, role 'owner'|'staff', perms, active)     -- ერთ ადამიანს რამდენიმე სასტუმრო შეიძლება ჰქონდეს
meta_pages   (page_id PRIMARY KEY, tenant_id, channel 'fb'|'ig', token_enc, connected)
seasons      (tenant_id, id, name, from_md, to_md, sort)                 -- სეზონები კოდიდან აქ გადადის
```

არსებული ცხრილები, ყველას ემატება `tenant_id`, გასაღები კი ხდება `(tenant_id, id)`:
`settings, types, rooms, bookings, payments, guest_notes, convos, site_content, actlog, login_fails`.
`media` ცხრილი რჩება, ოღონდ მხოლოდ R2-ის გასაღებით და ზომით.

ფასები ახლა `{ peak, winter, summer, off }`-ია. ის ხდება `{ [season_id]: ფასი }`, ასე რომ თითო სასტუმროს თავისი სეზონები ექნება. ვილა ჯიჯის ოთხი სეზონი ნაგულისხმევ შაბლონად რჩება მთის კურორტებისთვის.

### 2.6 შესვლა და უფლებები

- შესვლა ხდება **ელფოსტით და პაროლით** (PBKDF2, იგივე, რაც ახლა). „დამავიწყდა პაროლი“ ელფოსტით მუშაობს.
- `role = owner` ნიშნავს ყველა უფლებას, „სუფთა ფურცლით დაწყებას“ და გუნდის მართვას. დანარჩენი უფლებები იგივეა: `book, money, price, site`.
- **პლატფორმის ადმინი** (ჩვენ) ცალკე როლია: სასტუმროს შექმნა, დაპაუზება და მხარდაჭერისთვის შესვლა „სასტუმროს სახელით“. ეს ყოველთვის ჟურნალში იწერება.

### 2.7 საიტი: ერთი შაბლონი, სერვერზე შევსებული

- `index.html` ხდება ზოგადი შაბლონი. „აუზი“, „კინო-ოთახი“ და მსგავსი სექციები ჩართვადი ბლოკები ხდება.
- ტექსტები, ფოტოები, JSON-LD (`Hotel`), `hreflang`, sitemap და llms.txt **სერვერზე ივსება** (HTMLRewriter), და არა ბრაუზერში. ეს SEO-სთვის და Google-ისთვის მნიშვნელოვანია, რადგან ტექსტი გვერდის კოდშივე ჩანს.
- სამი ენა (ka/en/ru) რჩება. თარგმანები ბაზაშია, ადმინში სამივე ენის ველია.
- ფერი და ლოგო სასტუმროსია. Visit2-ის ნიშანი მხოლოდ ქვედა ზოლშია, პატარად: „Visit2.ge-ზე“.

### 2.8 Facebook და Instagram ბოტი

- **ერთი Meta აპი** Visit2-ის სახელით, ერთი webhook: `visit2.ge/api/meta`. შეტყობინებაში მოდის გვერდის ID, საიდანაც `meta_pages`-ით ვპოულობთ სასტუმროს.
- გვერდის მიერთება მეპატრონისთვის ერთი ღილაკია: „Facebook-ით შესვლა“ ადმინში. ჩვენ ვიღებთ გვერდის ტოკენს და დაშიფრულს ვინახავთ (გასაღები Cloudflare Secrets-შია).
- **App Review აქ უფრო დიდია**, ვიდრე ვილა ჯიჯიზე: სხვისი გვერდების მართვას სჭირდება `pages_messaging` და `instagram_manage_messages` უფლებების Advanced Access და Visit2-ის, ანუ LLC-ის, ბიზნეს-ვერიფიკაცია. ამიტომ ეს LLC-ის შექმნაზეა დამოკიდებული (ბრიფის მე-4 ნაწილი). სანამ ეს მზად არ არის, საპილოტე სასტუმროებს ბოტი მხოლოდ საიტზე ექნებათ.

### 2.9 გადახდები (Stripe)

- Stripe Checkout და Customer Portal: ბარათს Stripe-ის გვერდზე ვიღებთ, ჩვენთან ბარათის მონაცემები არ ინახება.
